# Billing (Paystack)

Modules: `src/lib/billing/paystack.ts`, `reference.ts`, `term.ts`, `entitlement.ts`, `settlement.ts`, `signature.ts`, `subscription-data.ts`. Routes: `src/app/api/billing/*/route.ts`. Design notes also live in `docs/superpowers/specs/2026-09-04-paystack-billing-design.md`; this file is the behaviour to port.

Tests: `scripts/test-billing-term.mts`, `test-billing-entitlement.mts`, `test-billing-signature.mts`, `test-billing-settlement.mts`, `test-subscription.mts`.

## When billing is off

`PAYSTACK_SECRET_KEY` missing, blank, or equal to `your-paystack-secret-key` → `billingEnabled` is false. Checkout returns **503**. The upgrade UI hides itself. Webhook verification cannot succeed without the same secret, because the HMAC key is that secret.

## Reference

`pw_` + UUID with hyphens removed (`src/lib/billing/reference.ts`). Generated by us and sent to Paystack as `reference`, so every transaction points at exactly one `Subscription` row.

## Term dates (UTC)

`src/lib/billing/term.ts`.

`termStart(now, currentEndsAt)`: if the student already has a live `endsAt` in the future, the next term starts at that `endsAt` (stacking). Otherwise it starts at `now`.

`termEnd(start, period)`: YEARLY adds 12 months, MONTHLY adds 1. `addMonthsUTC` clamps the day-of-month (31 January + 1 month → 28 or 29 February), so terms do not spill into the following month.

## What “live” means

`src/lib/billing/entitlement.ts`. A row covers `now` when all of:

- `status === ACTIVE`
- `endsAt` is not null
- `startsAt` is null or `startsAt <= now`
- `endsAt > now` (end is exclusive)

The richest live tier wins (`PREMIUM` over `STANDARD` over nothing). `expiresAt` returned to the UI is the **furthest** `endsAt` among rows of that winning tier. No live row → `{ tier: FREEMIUM, expiresAt: null }`.

`User.tier` is updated to this resolution by settlement, by the JWT refresh, and by admin grant/revoke. A stale `User.tier` can exist for up to the profile-cache TTL if nobody refreshes; entitlement denial re-reads the column, and the JWT callback also reconciles when it refreshes.

## Checkout

`POST /api/billing/checkout` (auth, 10/minute per user):

1. Billing enabled, else 503.
2. Validate `{ tier, period }`. Reject `FREEMIUM`.
3. User must have an email, else 400 (Paystack requires it).
4. `createPendingSubscription`:
   - Other `PENDING` rows for this user become `ABANDONED`.
   - Insert `PENDING`, `source=PAYSTACK`, server-side `amountKobo` from the price table (ignore any client amount), `currency=NGN`, new reference.
5. Paystack `POST /transaction/initialize` with that amount, email, reference, `callback_url = {NEXT_PUBLIC_APP_URL}/api/billing/callback`, metadata `{ userId, tier, period }`.
6. 200 `{ authorizationUrl }`. Paystack HTTP failure → 502. Do not mark the row `FAILED` on initialize failure; it stays `PENDING` until abandoned by the next checkout or left for the webhook.

Prices: see [03-auth-and-access.md](./03-auth-and-access.md). Amounts are kobo integers.

## Browser callback

`GET /api/billing/callback?reference=`

1. Missing reference → redirect `.../settings/billing?status=missing`.
2. `verifyTransaction` against Paystack’s verify endpoint.
3. `applyChargeSuccess`.
4. Redirect:
   - success, including `already-applied` → `status=success`
   - verify says the charge failed → `status=failed`
   - anything else (network, not yet successful) → `status=pending`

The webhook remains authoritative. The callback is a convenience so the settings page can update immediately. Do not grant access on the redirect alone if verify did not return success; `applyChargeSuccess` is the only writer.

## Webhook

`POST /api/billing/webhook`. Excluded from the session proxy.

1. Read the **raw** body bytes.
2. `x-paystack-signature` must equal HMAC-SHA512 of those bytes, keyed with `PAYSTACK_SECRET_KEY`, hex-encoded. Compare in constant time (`src/lib/billing/signature.ts`). Mismatch → 401 `{ "error": "Invalid signature" }`.
3. JSON parse. Failure → 400.
4. No reference in the payload → 200 `{ "received": true }` (nothing to apply).
5. `recordPaystackEvent`: insert `PaystackEvent` with `eventKey = "{reference}:{type}"` and the payload. Unique violation → 200 `{ "received": true, "duplicate": true }`.
6. If `type !== "charge.success"`, stop at 200. Other events are stored and ignored.
7. `verifyTransaction(reference)` — do not trust the webhook body for amount or status.
8. `applyChargeSuccess`. On throw: `forgetPaystackEvent` (delete the row) and return **500**, so Paystack retries. On a normal rejection outcome, return 200 with the outcome (the event stays recorded; retrying would not change a permanent mismatch).

## Settlement rules

`src/lib/billing/settlement.ts` decides whether a verified transaction may activate a row. `applyChargeSuccess` in `subscription-data.ts` performs the write.

Activate only when:

- the Paystack reference equals the row’s reference
- row status is `PENDING` or `ABANDONED` (the student may have started a newer checkout; a late success for the abandoned reference still grants the term they paid for)
- transaction `status === "success"`
- `amount` equals `amountKobo`
- `currency` equals the row currency (`NGN`)

| Situation | Outcome |
|---|---|
| No row for the reference | `unknown-reference` |
| Row already `ACTIVE` | `already-applied` |
| Transaction not successful | `not-successful`, and the row is set to `FAILED` if it was still pending |
| Amount differs | `amount-mismatch` (no activate) |
| Currency differs | `currency-mismatch` |
| Status not pending/abandoned (for example `REVOKED` or `FAILED`) | `not-pending` |

Activation `updateMany` is guarded on `status in (PENDING, ABANDONED)` so two deliveries cannot both apply. It sets `ACTIVE`, `paidAt`, `channel`, `startsAt`, `endsAt` (from `termStart` / `termEnd`, stacking on a current live end). Then it sets `User.tier` from a fresh resolution and refreshes the JWT tier cache (`refreshCachedTier` / `updateSession`) when a session exists.

Idempotency is three layers: the `PaystackEvent` primary key, the `already-applied` short-circuit, and the guarded `updateMany`.

## Admin comps

Not Paystack. `grantComp` and `revokeSubscriptions` in `subscription-data.ts`, called by the admin tier route.

- Comp: `source=COMP`, `amountKobo=0`, `status=ACTIVE`, `grantedById`, optional `note`, term dates from the same UTC month arithmetic, reference still unique (`pw_…`).
- Downgrade to freemium: all `ACTIVE` rows → `REVOKED`, then resolve tier (which becomes FREEMIUM if nothing else is live).

A comp and a Paystack term can overlap. The richest live tier wins, so a PREMIUM comp masks a STANDARD payment until the comp’s `endsAt`. Revoke does not refund Paystack.

## Currency and channels

Only `NGN`. `channel` is whatever Paystack reports (`card`, `bank`, `ussd`, …) and is stored for support, not for logic.
